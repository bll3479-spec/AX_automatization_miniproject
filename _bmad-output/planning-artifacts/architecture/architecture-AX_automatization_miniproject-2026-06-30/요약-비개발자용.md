# 자봐 — 이번 작업 설계 요약 (비개발자용)

> 이 문서는 `ARCHITECTURE-SPINE.md`(개발자/AI 에이전트용 설계 문서)를 쉬운 말로 풀어 쓴 요약이다. 코드를 직접 보지 않아도 "무엇을 바꾸고, 무엇은 손대지 않는지"를 이해할 수 있도록 작성했다.

## 이 문서가 다루는 범위

PRD에서 정한 4가지 기능(F1~F4)을 실제로 구현하기 전에, "여러 부분을 동시에 작업해도 서로 어긋나지 않도록" 미리 정해둔 규칙들이다. 비유하자면 — 여러 사람이 같은 건물을 나눠서 지을 때, 전기 배선 규격이나 기둥 위치를 미리 합의해두는 것과 같다. 합의가 없으면 나중에 합쳤을 때 안 맞는 부분이 생긴다.

## 지금 앱이 동작하는 방식 (그대로 유지)

```
사용자 화면(웹)  →  서버(API)  →  분류 엔진 / Gmail 연동
```

- **분류 엔진**(`classifier.py`): 메일의 제목·발신자·키워드를 보고 점수를 매겨 카테고리를 정한다. 점수 계산 공식 자체는 이번에도 건드리지 않는다.
- **서버**(`main.py`): 화면 요청을 받아 분류 엔진과 Gmail을 연결해주는 얇은 중계 역할만 한다.
- **화면**(`app.js`): 전체 상태를 하나의 덩어리로 들고 있다가, 뭔가 바뀌면 화면 전체를 다시 그린다.

이 구조 자체는 이번 작업에서 바꾸지 않는다. PRD의 4개 기능은 이 구조 "안에서" 확장하는 것이다.

## 절대 건드리지 않는 것 2가지

1. **보안 메일 보호 장치**: 인증번호·비밀번호 재설정처럼 민감한 메일로 판정되면, 그 내용은 절대로 외부 AI(LLM)에게 전달되지 않는다. 이 장치는 코드 두 군데에서 한 쌍으로 동작하는데, 이번 작업에서 이 쌍을 분리하거나 약화시키는 것은 금지한다.
2. **점수 계산 공식**: "키워드 1개당 1점, 발신자 매칭 1개당 2점" 같은 계산 방식 자체는 그대로 둔다. 새 카테고리나 키워드를 추가할 때도 이 공식을 바꾸는 게 아니라, 계산에 들어가는 "재료 목록"(키워드/발신자 리스트)만 늘린다.

## 이번에 새로 정한 규칙 2가지

### 규칙 1 — "메일 목록 가져오기"와 "분류하기"를 분리한다 (진행률 표시 기능용)

기존에는 메일을 가져오는 것과 분류하는 것이 한 번의 요청으로 묶여 있어서, 처리 중간 상황을 화면에 보여줄 방법이 없었다.

**바뀌는 방식**: 먼저 메일 목록을 한 번만 가져온 뒤, 그 목록을 작은 묶음(배치)으로 나눠서 여러 번에 걸쳐 분류한다. 한 묶음이 끝날 때마다 "300건 중 120건 처리됨" 같은 진행률을 화면에 표시할 수 있게 된다.

이렇게 하는 이유: 묶음마다 Gmail에서 메일을 다시 가져오면 ① Gmail API 호출 횟수 제한에 낭비가 생기고 ② 묶음마다 가져오는 메일이 미묘하게 달라져서 "총 건수"가 흔들릴 수 있다. 그래서 가져오기는 1번, 분류는 여러 번으로 명확히 나눴다.

### 규칙 2 — 여러 건의 수정을 "모았다가 한 번에" 반영한다 (일괄 적용 기능용)

기존에는 카테고리를 수동으로 한 건 고칠 때마다 전체 메일을 즉시 다시 분류했다. 여러 건을 고치고 싶으면 매번 기다려야 했다.

**바뀌는 방식**: 사용자가 여러 건을 고치는 동안에는 화면(브라우저)에만 임시로 저장해두고, 서버에는 아무것도 보내지 않는다. 사용자가 "적용" 버튼을 눌렀을 때만 ① 모아둔 수정 건수만큼 서버에 순서대로 보내고 ② 전체 재분류는 딱 한 번만 실행한다.

기존에 한 건씩 수정하던 API 자체는 그대로 둔다 — "여러 번 부르는 방식 + 마지막에 한 번 재분류"로 화면(프론트엔드) 쪽에서만 묶어주는 방식이라, 서버 쪽 코드를 새로 만들 필요가 없다.

## 새 카테고리 "보고서 및 간행물"

서울시·국회예산정책처에서 오는 공식 발간물 메일이 지금까지는 "기타"로 빠졌는데, 별도 카테고리를 하나 추가해 명확히 분류되게 한다. 기존 6개 카테고리 체계에 1개를 더하는 것뿐이고, 분류 로직의 구조(점수 계산 방식)는 똑같이 유지한다.

## 이번에 하지 않는 것 (다음 라운드로 미룸)

- 영수증(결제) 카테고리를 "결제 내역"과 "결제 수단 변경"으로 세분화하는 것 — 화면·서버·분류 엔진 3곳을 동시에 고쳐야 해서 부담이 크다.
- 사용자가 카테고리를 직접 만들 수 있는 기능 — 지금 앱은 데이터베이스가 없어서(메모리에만 저장), 영구 저장이 필요한 이 기능은 저장 방식부터 다시 고민해야 한다.
