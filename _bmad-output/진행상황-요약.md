# 자봐 프로젝트 — BMAD 파이프라인 진행상황 요약

> 이 문서는 지금까지 어떤 단계를 거쳐왔고, 각 단계가 무엇을 하는 작업인지, 어떤 파일이 만들어졌는지를 처음 보는 사람도 이해할 수 있도록 정리한 것이다. 코드를 직접 보지 않아도 전체 흐름을 알 수 있게 작성했다.

## 한눈에 보는 전체 흐름

```
1단계: 브리프        →  2단계: PRD         →  3단계: 아키텍처      →  4단계: 에픽/스토리   →  5단계: 실제 코드 구현
(문제가 뭔지 정리)      (뭘 만들지 정의)        (어떻게 만들지 규칙)     (작업 단위로 쪼개기)     (아직 진행 안 함)
   ✅ 완료                ✅ 완료                 ✅ 완료                ✅ 완료                ⬜ 다음 단계
```

이게 BMAD 방식의 기본 패턴이다 — "문제 발견 → 무엇을 만들지 → 어떻게 만들지(설계 규칙) → 작업 쪼개기 → 코드 작성" 순서로 한 단계씩 구체화해가는 것이다. 각 단계는 앞 단계의 결과물을 입력으로 받아서 더 구체적인 결과물을 만든다.

## 단계별 설명

### 1단계: 브리프 (Brief) — "문제가 뭔지 정리"

**한 일:** 실제 Gmail 메일함을 조사해서 분류가 잘못된 사례들(프로모션 메일이 결제로 분류되는 등)을 발견하고, 그 증거(발신자 주소, 메일 제목, 점수 계산)를 정리했다.

**결과물:**
- `planning-artifacts/briefs/brief-AX_automatization_miniproject-2026-06-30/brief.md` — 문제 요약본
- `planning-artifacts/briefs/.../addendum.md` — 사례별 원본 증거(발신자 주소, 점수 계산 근거 등 상세 데이터)

### 2단계: PRD (Product Requirements Document) — "뭘 만들지 정의"

**한 일:** 브리프에서 발견한 문제들을 실제로 "무엇을(what)" 고칠지 기능 단위로 정의했다. 4개의 기능(F1~F4)과 그 안의 세부 요구사항(FR-1~12), 그리고 "이건 절대 바꾸면 안 된다"는 제약사항(NFR-1~4)을 정했다.

**정해진 4개 기능:**
- F1. 분류 규칙 정확도 보강 (오분류 사례 수정)
- F2. 신규 카테고리 "보고서 및 간행물" 추가
- F3. 분류 진행률 UI (% 표시)
- F4. 수동 정정 일괄 적용 플로우 ("적용" 버튼 한 번으로 모아서 반영)

**결과물:**
- `planning-artifacts/prds/prd-AX_automatization_miniproject-2026-06-30/prd.md`

### 3단계: 아키텍처 스파인 (Architecture Spine) — "어떻게 만들지 설계 규칙"

**한 일:** PRD에서 정한 기능들을 구현할 때 "여러 부분을 동시에 작업해도 서로 어긋나지 않도록" 지켜야 할 설계 규칙(불변사항)을 정했다. 비유하자면 여러 사람이 한 건물을 나눠 지을 때 전기 배선 규격을 미리 합의해두는 것과 같다.

**정한 핵심 규칙 4가지(AD-1~4):**
- 보안 메일 보호 장치는 절대 약화시키지 않는다
- 분류 점수 계산 공식은 그대로 두고, 키워드/발신자 "재료 목록"만 늘린다
- 메일 목록 가져오기와 분류하기를 분리한다 (진행률 표시를 위해)
- 여러 건의 수정을 모았다가 한 번에 반영한다 (일괄 적용을 위해)

**결과물:**
- `planning-artifacts/architecture/architecture-AX_automatization_miniproject-2026-06-30/ARCHITECTURE-SPINE.md` — 개발자/AI 에이전트용 설계 문서
- `planning-artifacts/architecture/.../요약-비개발자용.md` — 같은 내용을 쉬운 말로 풀어 쓴 버전 (이 문서와 비슷한 성격)

### 4단계: 에픽/스토리 분해 (Epic/Story Breakdown) — "작업 단위로 쪼개기"

**한 일:** PRD의 4개 기능과 아키텍처 규칙을 실제로 코드를 작성할 수 있는 작은 작업 단위("스토리")로 잘게 쪼갰다. 각 스토리는 "누가, 무엇을, 왜 원하는지" + "이게 됐다고 확인할 수 있는 구체적인 기준"으로 구성된다.

**완성된 구조 — 4개 에픽, 12개 스토리:**

| 에픽 | 내용 | 스토리 수 |
| --- | --- | --- |
| Epic 1 | 분류 규칙 정확도 보강 | 3개 (1.1~1.3) |
| Epic 2 | 신규 카테고리 "보고서 및 간행물" | 3개 (2.1~2.3) |
| Epic 3 | 분류 진행률 UI | 3개 (3.1~3.3) |
| Epic 4 | 수동 정정 일괄 적용 플로우 (Epic 3 이후 진행) | 3개 (4.1~4.3) |

**결과물:**
- `planning-artifacts/epics.md` — 전체 요구사항 + 4개 에픽 + 12개 스토리 전체

### 5단계: 실제 코드 구현 — 다음 단계 (아직 시작 안 함)

`epics.md`의 스토리를 Epic 1부터 순서대로 하나씩 구현하면 된다. 각 스토리는 독립적으로 완료 가능하도록 설계되어 있어서, 한 번에 다 만들 필요 없이 스토리 단위로 나눠서 진행할 수 있다.

## 지금까지 만들어진 파일 한눈에 보기

```
_bmad-output/
├── project-context.md                          # 기존 코드베이스 분석 메모 (브라운필드 컨벤션)
├── 진행상황-요약.md                              # 이 문서
└── planning-artifacts/
    ├── briefs/brief-.../
    │   ├── brief.md                            # 1단계: 문제 정리
    │   └── addendum.md                         # 1단계: 원본 증거 데이터
    ├── prds/prd-.../
    │   └── prd.md                              # 2단계: 무엇을 만들지
    ├── architecture/architecture-.../
    │   ├── ARCHITECTURE-SPINE.md               # 3단계: 어떻게 만들지 (설계 규칙)
    │   └── 요약-비개발자용.md                    # 3단계: 쉬운 말 버전
    └── epics.md                                # 4단계: 작업 단위로 쪼갠 것 (4 에픽 12 스토리)
```

각 단계 폴더 안의 `.memlog.md` 파일들은 작업 과정에서 오간 결정 사항들의 기록(작업 일지)이라 평소에는 안 봐도 된다.
